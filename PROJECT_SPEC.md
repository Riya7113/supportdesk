# SupportDesk Project Specification

**Project owner:** Riya Singh

SupportDesk is a multi-tenant customer support application. Each workspace belongs to one organization. Organization members sign in, track tickets, and write replies. A member must never read or change another organization's information.

## Product requirements

### Accounts and workspaces

- A person can register a workspace with an organization name, name, email address, and password.
- Registration creates the first account as that workspace's administrator.
- Passwords are stored as Argon2 hashes, never as readable text.
- Sign-in returns a time-limited signed access token.
- Administrators can create agent accounts. Email invitations are not part of the current release.
- Each account belongs to one organization and has either the `admin` or `agent` role.

### Tickets and conversations

- A member can create a ticket with a subject, description, and priority.
- Priority is `low`, `normal`, `high`, or `urgent`.
- Status is `open`, `in_progress`, or `resolved`.
- Members can list, search, filter, and view tickets in their organization.
- Members can change ticket status and priority and add replies.
- Administrators can assign a ticket to an active member of the same organization.
- The overview shows counts by status, unresolved urgent tickets, and recently updated tickets.

### Tenant isolation

- The API derives organization access from the authenticated account, not from a client-supplied organization ID.
- Every ticket, comment, team list, dashboard query, and assignment is restricted to the current account's organization.
- A ticket in another organization is reported as not found.
- The database stores organization IDs on tenant-owned records and uses foreign keys and constraints to protect relationships.

## Technology

- Frontend: React, TypeScript, Vite, Tailwind CSS
- Backend: Python, FastAPI, Pydantic Settings, SQLAlchemy 2.x, Alembic
- Database: PostgreSQL
- Deployment: Vercel for the frontend; Render's native Python service and managed PostgreSQL for the API and database
- Password hashing: Argon2 through `pwdlib`
- Signed access tokens: JWT using `PyJWT`

## Architecture

```text
Browser
  | HTTPS JSON requests to /api/v1
  v
Vercel static hosting (React frontend)
  | HTTPS requests allowed by the API's CORS_ORIGINS setting
  v
Render native Python web service (FastAPI API)
  | SQLAlchemy 2.x
  v
Render managed PostgreSQL
```

FastAPI owns configuration, authorization, and business rules. Database schema changes are versioned with Alembic. Render applies pending migrations before starting the API. The frontend API address and API browser-origin allowlist are configured separately through provider environment settings.

## Local development

- Copy `.env.example` to `backend/.env` and set a local PostgreSQL address and signing secret.
- Install backend dependencies in a Python virtual environment and run Alembic and Uvicorn from `backend/`.
- Run `npm ci` and `npm run dev` from `frontend/`.
- The frontend is at <http://localhost:5173>; the API is at <http://localhost:8000>.
- `/health` checks that the API process responds; `/ready` also checks PostgreSQL.
- API documentation is available at `/docs` during local development.

## Deployment

`frontend/vercel.json` configures the Vite single-page application for Vercel. `render.yaml` describes a native Python web service and a managed PostgreSQL database without Docker. Render runs database migrations before the API starts. Set `CORS_ORIGINS` to the deployed Vercel origin. `SECRET_KEY` is generated by Render and `DATABASE_URL` is linked to the managed database, not committed to the repository.

The Render database plan configured in `render.yaml` is paid so the database does not expire like Render's free PostgreSQL databases. The operator must review current costs and configure backups and restore checks before storing important customer data. The free API plan can sleep when idle.

## Not included in this release

- Email verification, password reset, multi-factor authentication, and emailed invitations
- External email or chat notifications
- Attachments, billing, customer self-service portals, and audit exports
- Automated database backup storage

The deployment guide describes a production-oriented container setup, but this release has not been independently security audited. Add account recovery, sign-in rate limiting, operational backups, and organization-specific policies before relying on it for sensitive or regulated data.
